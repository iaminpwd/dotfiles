# 근거 충실성 원칙 (Fidelity & Anti-Hallucination)

다이어그램 생성 시 명시된 리소스만 렌더링하는 표준임.

## 0. 입력 모드 판별 (Input Mode Detection)

- **[MUST]** 사용자가 IaC 코드/리포지토리 경로를 제공했다면 "코드 기반 모드"(1~4절 적용)를, 텍스트 설명만으로 요청했다면(예: "EKS 2개와 NAT Gateway를 쓴다") "설명 기반 모드"(§6 적용)를 적용할 것.
- **[MUST]** 코드와 설명이 함께 제공된 경우 코드를 SSOT로 삼으십시오. 설명은 코드만으로 알 수 없는 세부사항(예: 클러스터가 실제로 무엇을 실행하는지, 운영 상태)을 보완하는 근거로만 사용하고, 설명이 코드 내용과 상충하면 사용자 질문을 통해 명확히 확인할 것.

## 1. 활성/비활성 리소스 구분

- **[MUST]** 주석 처리된 블록(`# module "x" {...}`)이나 `count = 0`으로 평가되는 조건부 리소스는 "현재 배포되지 않음"으로 취급하여 다이어그램에서 제외할 것.
- **[MUST]** 단, 코드 주석이나 `README.md`에 "Terraform 외부에서 수동 운영 중"처럼 실제 가동 중임이 명시된 경우에는 포함하되 "(수동 관리)"와 같이 상태를 라벨에 표기할 것.

<examples>
<example>
[Bad] `# module "rds" { ... }`(전체 주석 처리, TODO 표시)를 근거로 "RDS (PostgreSQL)" 노드를 실존 리소스처럼 생성
</example>
<example>
[Good] 동일 상황에서 RDS 노드를 생성하지 않거나, 반드시 표기해야 한다면 "RDS (PostgreSQL) — 미배포/TODO"로 명시
</example>
</examples>

## 2. README/모듈 주석을 1차 근거로 사용

- **[MUST]** 리소스 블록 파싱만으로 마무리하는 대신 프로젝트 `README.md`(아키텍처 개요, 네트워크 구성 표)와 각 모듈 상단 주석을 함께 읽으십시오.
- **[MUST]** README에 서브넷별 CIDR·용도 표가 존재하면 그것을 서브넷 분할의 SSOT로 삼으십시오.

## 3. 클러스터 내부 워크로드 반영

- **[MUST]** EKS/AKS 등 클러스터 리소스 자체만 그리고 마무리하는 대신, 모듈 주석·README·Helm/values 파일에서 그 클러스터가 실제로 무엇을 실행하는지(예: CI/CD 도구, 메시지 브로커) 찾아 아이콘으로 반영할 것.
- **[MUST]** 근거를 찾지 못하면 일반 명칭("EKS Cluster")만 사용하고 구체적 워크로드 아이콘을 명시된 객체만 정확히 반영할 것.

## 4. 예외적 운영 상태 반영

- **[MUST]** README에 "현재 X는 Y 내부에서 운영 중"처럼 설계와 다른 실제 운영 방식이 명시된 경우, 설계도상 위치가 아니라 실제 운영 위치를 반영할 것.

## 5. 불확실하면 질문

- **[MUST]** 코드·문서 어디에서도 근거를 찾을 수 없는 구성 요소는 그럴듯하게 추측해서 채우는 대신 사용자에게 확인할 것.

## 6. 설명 기반 모드의 근거 충실성 (Description-Driven Mode)

본 절은 IaC 코드 없이 자연어 설명만으로 다이어그램을 생성할 때(§0에서 "설명 기반 모드"로 판별된 경우) 적용됨. 코드가 없으므로 "근거"는 사용자의 발화 자체이며, 코드 기반 모드의 1~4절과 동일한 원칙(명시 리소스만 렌더링, SSOT 우선, 불확실하면 질문)을 발화 텍스트에 적용함.

- **[MUST] 명시된 요소만 정확한 종류·수량으로 반영**: 사용자가 언급한 리소스 종류와 수량(예: "EKS 2개", "NAT Gateway")은 그 개수와 종류를 정확히 반영할 것. 언급되지 않은 리소스를 실제 있는 것처럼 명시된 객체만 반영할 것.
- **[MUST] 미명시 세부사항은 표준 기본값 + 명시적 라벨링**: 리소스 종류/수량은 명시했지만 배치 구조(AZ 개수, 서브넷 CIDR, VPC 구성 등)를 언급하지 않았다면 AWS/Azure Well-Architected 기준 표준 레퍼런스 아키텍처(예: 2-AZ Public/Private 서브넷 분리)를 기본값으로 채우십시오. 이때 해당 노드/서브넷 라벨에 `(가정: 표준 2-AZ 구성)`처럼 추정값임을 반드시 명시하여 사용자 명시 요소와 구분되게 하십시오.
- **[MUST] 중대한 모호성은 기본값으로 임의 확정하는 대신 질문**: 기본값을 채우기에는 리소스 배치나 개수에 미치는 영향이 큰 모호성(예: NAT Gateway가 1개 공용인지 AZ마다 1개인지, EKS 2개가 같은 VPC인지 별도 VPC/리전인지)이 있다면 base 코어 룰의 [Halt on Confusion] 원칙에 따라 먼저 사용자에게 확인할 것.
- **[MUST] 근거 출처 구분 표기**: XML 생성 후, 어떤 노드가 "사용자 명시" 근거이고 어떤 노드가 "표준 기본값 추정"인지 다이어그램 내 라벨(예: `(기본값)` 접미사) 또는 별도 목록으로 구분 가능하게 남기십시오. 라벨 표기 형식 자체는 010-drawio-xml-standard.md의 라벨링 규칙을 그대로 따르십시오.

<examples>
<example>
[Bad] "EKS 2개와 NAT Gateway를 쓴다"는 설명만으로 RDS, ElastiCache 등 언급되지 않은 리소스까지 "일반적으로 EKS와 같이 쓰이니까" 임의로 추가
</example>
<example>
[Good] 동일 설명에서 EKS 클러스터 2개와 NAT Gateway만 그리고, AZ 배치는 표준 2-AZ 기본값을 적용하되 라벨에 "(가정: 표준 2-AZ 구성)"을 표기. NAT Gateway 개수(1개 vs AZ당 1개)가 배치에 미치는 영향이 크므로 사용자에게 확인
</example>
</examples>
